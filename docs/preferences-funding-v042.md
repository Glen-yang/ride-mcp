# Preferences and trading-account funding · 0.4.2

Recommendations return structured missing questions before reading candidates. `get_preferences` reads saved/partial answers; `set_preferences` merges supplied answers and returns remaining questions. Budget, acceptable loss and market are required; explicit basket/Fixed choices require their size/entry amount. Existing answers and portfolios are retained. The card starts with empty budget/loss and an unselected market. AI instructions forbid invented values.

`get_deposit_address` and `check_deposit_status` distinguish receiving-wallet USDC from verified trading collateral. `prepare_deposit` freezes an exact amount and owned account, returns a human confirmation URL, and moves no funds. The browser can review a changed amount, then separately confirm funding and any required account activation. Embedded owners sign the existing Core Permit/approveAgent challenges; server-master owners explicitly confirm the existing Core relayer operation. Signatures/challenges are absent from MCP output. All confirmation requests use authenticated Core identity and browser CSRF; no machine confirmation tool is registered.

The funding identity is durably consumed before external submission. Concurrent confirmations submit once; uncertain results block new funding requests. Credit requires the matching native-USDC Transfer log to the fixed Arbitrum bridge and observed trading available balance; wallet credit alone is insufficient. Prediction status also reads verified trading collateral instead of treating provider completion as ready.

The isolated Core API opts in with `RIDE_AGENT_FUNDING_ENABLED=true` and `RIDE_AGENT_INTERNAL_ONLY=true`. Its adapter reuses existing funding, wallet-generation, signature-verification and writer-lease capabilities. Other API deployments cannot use this route. Only the isolated API receives references to existing relayer/Privy credentials; automatic deposit/close workers stay disabled. No old App binary, GraphQL/RPC contract, table migration or service deployment is changed.

Acceptance before deployment: 103 TypeScript/PostgreSQL checks; 38 HTTP/MCP/OAuth/CLI/Pg scenarios using simulated identities and transactions; two Core read-only/epoch checks. Browser fixture verified missing-preference gating and funding confirmation through observed trading balance. Fixtures do not establish a real financial transaction. The signed-in Glen account is reserved for human-confirmed production acceptance.

Limits: transfers still require the user's confirmation/signature. Unknown broadcasts require reconciliation, not another submission. Existing account ownership fences remain enforced. Funding to the Core Perps scope does not automatically move collateral into an RWA DEX scope. Physical App push/release remains separate.
