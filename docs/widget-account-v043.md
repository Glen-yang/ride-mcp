# Widget, accounts and trader-count repair (0.4.3)

The preference form previously injected Crypto/BTC/ETH restrictions, and `market=both` required cross-market allocation. Eleven otherwise eligible Perps traders could therefore fail with a hardcoded three-trader diversification message. The form now has one asset preference control, defaulting to `any`, `[]`, and `allow_altcoins=true`. Existing explicit saved choices remain visible. Market selects the allowed universe: either market may be the only market in a returned plan, and that coverage is disclosed.

Candidates are returned and rendered independently of plan generation, including structured error responses. The list shows scores, assets, eligibility, budget qualification, total count, detail/selection controls and local pagination. Single and 2–8 trader plans share one count control. An explicit count is never silently reduced; failures offer feasible alternatives with unchanged risk and loss settings. Allocation minimums are applied before selection. Diagnostics include an ID, failure stage, sequential counts, per-trader exclusions, affected fields, current/required values and count actions. There is no generic success-status text in the Widget.

`get_portfolio` returns `account_balances` separately from Agent and App copies. Copy allocation remaining and Agent bookkeeping are not additional account cash. Perps reads authenticated wallet generations and deduplicates them, matching the App's Classic/Unified equity and Spot valuation rules. Prediction verifies pUSD/USDC.e/native-USDC balances at one Polygon block, independently of the legacy GraphQL zero fallback, and reads complete owned position inventory with pagination. Retained Prediction cash is included in equity but separated from current-wallet availability; the response explains any App display difference. Native USDC funding cash is reported separately from trading equity. Source times and fetch times remain distinct. Reserves absent from the source stay null.

Meme is a separate App wallet/inventory module. Its complete authenticated multi-chain valuation is not exposed by the current account API, so it is explicitly unsupported with null values. The full account total remains null; the verified subtotal includes covered modules only. Every failed, foreign, stale, incomplete or unpriced source remains unavailable rather than zero. Public venue/RPC reads receive only addresses verified by the authenticated Core session; they never receive a Ride token. A shared 22-second deadline bounds balance reads.

New plans carry internal asset-filter metadata. Previously approved plans/portfolios retain their prior execution semantics. Editing an old unrestricted plan produces a new canonical preview and does not mutate the old one. Account coverage cannot overwrite authoritative partial-fill, uncertain or settling execution states. MCP public input schemas remain compatible with the released 0.4.2 clients. The live guide explains the new defaults, candidate errors, account data and count semantics without a new login.

Validation before rollout: TypeScript checks, PostgreSQL-backed unit tests, HTTP/MCP/OAuth/CLI/Pg functional scenarios, package install/setup checks for Codex/Claude Code/Cursor, and browser use of the actual cards and backend with simulated account/venue sources. Regression inputs include 200 USDC, both markets, any assets, medium risk, 10% loss trigger and eleven Perps candidates, with exact 1/2/3/4 trader previews; two candidates retain the list and offer 1/2 instead of changing a four-person request silently. Browser confirmation is simulated and proves no real transfer, signature or exchange fill.

Rollout scope: the independent ride-mcp gateway and agent-backend only. No Rust service, App binary, legacy API/gRPC/worker, schema migration or production preference rewrite is required. Apple login remains deferred. Before/after deployment IDs and legacy readiness are acceptance evidence; local success alone is not production verification.

Local reproduction: `RIDE_AGENT_TEST_DATABASE_URL=postgresql:///DISPOSABLE_DB npm test`; `RIDE_AGENT_FUNCTIONAL_DATABASE_URL=postgresql:///DISPOSABLE_DB npm run test:functional`. Widget fixture: `RIDE_PREVIEW_PORT=17870 RIDE_PREVIEW_POOL_SIZE=11 RIDE_PREVIEW_WIDGET_REGRESSIONS=1 npm run preview:cards`. Loopback fixture endpoints and simulated financial actions are not production features.
